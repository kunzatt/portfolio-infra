주요 성과
캐시 호환성 지문 기반 배포 게이트 — 판단할 수 없으면 배포를 멈추는 Fail-Closed 배포

[문제 상황] API 서버와 캐시 서버가 분리되어 있어, 캐시 서버가 보유한 데이터 구조와 호환되지 않는 API를 배포하면 배포 직후 조회·저장이 깨질 수 있었습니다. 불일치를 해소하려고 캐시 서버를 자동으로 재기동하면 데이터 복구 범위가 커지는 위험도 있었습니다.

[해결 방안] 배포 후보 빌드와 실행 중인 캐시 서버에서 각각 SHA-256 호환성 지문을 계산해 기존 API 컨테이너를 내리기 전에 비교하도록 배포 스크립트를 구성했습니다. 지문이 다르거나 조회에 실패하면 배포를 중단하고, 캐시 서버 재기동은 자동으로 수행하지 않고 수동 확인을 거치도록 했습니다. 자동 배포에서는 차단된 커밋을 기록해 두고, 캐시 지문이 바뀌기 전까지는 같은 빌드를 반복하지 않도록 했습니다.

[결과] 릴리스 링크는 Health Check를 통과한 뒤에만 현재 버전으로 전환하고 이전 버전 링크를 함께 보존해 즉시 롤백할 수 있게 했습니다. 호환되지 않는 배포가 운영 중인 캐시 데이터에 영향을 주기 전에 차단하는 배포 기준을 마련했습니다.

캐시 서버 자원 고갈 장애 대응 — 힙·디스크·커넥션 상한과 영속 스토어 내구성 강화

[문제 상황] Node 저장소인 Infinispan 캐시 서버에서 캐시별 엔트리 상한이 누적되어 힙이 고갈되고, 약 500MB 크기의 영속 파일은 비정상 종료 시 복구 범위가 컸습니다. 요청마다 HTTP Client를 생성해 Ephemeral Port가 고갈되었고, 헬스 프로브가 좀비 프로세스로 남는 문제도 있었습니다.

[해결 방안] 캐시당 엔트리를 25,000개로 제한하고 SoftIndex 영속 파일 크기를 32MB로 줄이며 Graceful Stop을 추가했습니다. 릴레이 요청은 공유 커넥션 풀(전체 64, Route당 32)로 전환하고, 헬스 프로브에는 5초 타임아웃과 컨테이너 init 프로세스를 적용했습니다. 수백만 Node를 메모리에 올리는 무결성 감사는 AtomicReference CAS로 단일 실행을 보장했습니다.

[결과] 디스크 여유 공간이 2GiB 또는 10% 미만이면 쓰기를 507로 차단하고, 공간 확인 자체가 실패해도 차단하는 Fail-Closed 게이트를 적용했습니다. 캐시 서버가 같은 Consumer Group에 참여해 사용량 이벤트를 가져가던 문제도 설정 플래그로 Consumer를 API 서버에만 활성화해 분리했습니다.

캐시 데이터 자가 복구 — Object Storage 기반 부팅 시 복원과 백필

[문제 상황] 캐시 디렉터리를 교체하거나 비우면 워크스페이스·모듈 목록이 빈 결과로 조회됐습니다. 목록 쿼리는 캐시 서버의 Lucene 인덱스 위에서 동작해 원본 저장소로 지연 조회할 수 없었고, 로컬 개발 환경은 모두 같은 저장소 경로를 공유해 개발자 간 워크스페이스 데이터가 섞였습니다.

[해결 방안] 부팅 시 설정 데이터 재적재 → 우선 복원 → 전체 타입 복원 → 역방향 백필 순서로 동작하는 복원 로더를 구현하고, 키 단위 병렬 복원과 건수 검증을 적용했습니다. 복원 중에는 저장소로 다시 쓰지 않도록 가드를 두었고, 수동 복원 트리거도 제공했습니다.

[결과] 개발·운영 환경은 캐시와 Object Storage를 양방향으로 동기화해 캐시 유실 후에도 자동으로 복구되도록 하고, 로컬 환경은 미러링을 끄고 로컬 캐시만 사용하도록 분리해 데이터 혼선을 차단했습니다.

시크릿 관리 체계 정비 — 설정 파일의 API Key를 암호화 저장소와 환경 변수 주입으로 이관

[문제 상황] 외부 AI·협업 도구 API Key, 클라우드 자격 증명, JWT·OAuth 키가 환경 설정 파일에 흩어져 있어 저장소에 시크릿이 남고, 키를 교체할 때마다 설정 파일 수정과 재배포가 필요했습니다.

[해결 방안] 플랫폼 저장소에 암호화된 시크릿을 먼저 조회하고, 없을 때만 환경 변수로 Fallback하는 시크릿 서비스를 구현했습니다. 부팅 시 멱등하게 동작하는 Importer로 기존 값을 이관하고, AI 클라이언트·협업 도구·클라우드 SDK·인증 모듈이 모두 같은 경로로 시크릿을 읽도록 전환했습니다.

[결과] 암호화 키는 설정 파일의 리터럴을 제거하고 환경 변수로만 주입하도록 바꿔, 저장소에 커밋되는 시크릿을 제거했습니다. 시크릿 영속 데이터는 Object Storage 미러링으로 보강해 캐시 유실 시에도 복원되도록 했습니다.

외부 API 응답 신뢰성 문제 해결 — 데이터 검증 및 가공 레이어 설계

[문제 상황] 날씨, 버스, 지하철, 유튜브 등 다수의 외부 API를 연동했는데, OpenWeatherMap 예보 API에서 현재 기온이 25도임에도 최고 기온이 22도로 응답하는 등 논리적으로 맞지 않는 데이터가 유입되는 문제가 발생했습니다. 지하철 API는 "수인분당선", "경의중앙선"처럼 숫자가 없는 노선명을 반환해 단순 파싱이 불가능했습니다.

OpenWeatherMap 예보 API는 미래 시간대 기준으로 최고/최저 기온을 산출하기 때문에 현재 기온과 예보 기온 간의 논리적 불일치가 발생했습니다. 또한, 지하철 API는 노선명 포맷이 일관되지 않아 숫자 추출 방식으로는 처리할 수 없었습니다.

[해결 방안] 서비스 레이어에서 외부 API 응답을 그대로 전달하지 않고, 유효성 검증 및 데이터 가공을 담당하는 처리 로직을 설계했습니다. 현재 기온이 예보 최고/최저 범위를 벗어나면 직접 보정하는 로직을 추가했고, 지하철 호선명↔번호 매핑 테이블을 직접 구현했습니다. 또한 날씨 데이터를 기반으로 옷차림 추천, 우산 필요 여부 등 사용자에게 의미 있는 형태로 가공하여 응답하도록 구성했습니다.

[결과] 외부 API의 이상 응답에도 일관된 데이터 제공, 단순 데이터 중계가 아닌 도메인 로직이 담긴 서비스 레이어 구현

이중 재고 관리, Optimistic Lock — 장바구니 선점 재고와 오버셀 방지 설계

[문제 상황] 이커머스 재고 관리에는 두 가지 문제가 맞물려 있었습니다. 첫째, 장바구니에 상품을 담아둔 시간 동안 재고를 어떻게 처리할 것인가의 문제입니다. 주문 시점에만 재고를 차감하면, 여러 사용자가 동시에 장바구니에 담고 주문하는 경우 재고 초과가 발생할 수 있었습니다. 둘째, 동일 상품에 대한 동시 주문이 들어올 때 읽기-수정-쓰기 사이의 타이밍 차이로 실제 재고 이상의 주문이 처리되는 오버셀 문제가 있었습니다.

단순히 주문 시점에 재고를 차감하면 장바구니 단계에서의 선점이 없어 오버셀에 취약하고, 반대로 장바구니 추가 시 즉시 차감하면 장바구니 이탈 사용자로 인한 재고 고착 문제가 생겼습니다.

[해결 방안] stockQuantity(실제 재고)와 reservedQuantity(선점 재고)를 분리한 이중 재고 구조를 설계했습니다. 장바구니 추가 시 reserveStock()으로 선점 재고를 증가시켜 가용 재고를 선점하고, 주문 확정 시 decreaseStock()으로 실제 재고를 차감하는 방식입니다. 여기에 @Version 기반 Optimistic Lock을 적용해 동시 요청이 들어올 경우 커밋 시점에 버전 충돌을 감지하여 오버셀을 방지했습니다.

[결과] 장바구니 추가부터 주문 확정까지 전 과정에서 재고 일관성 확보, Optimistic Lock으로 동시 요청 오버셀 방지

k6 부하 테스트로 장바구니 N+1 문제 발견 — p95 응답시간 2,300ms → 120ms (95% 개선)

[문제 상황] k6로 장바구니 조회 API에 50 VU 동시 부하 테스트를 진행한 결과, p95 응답시간이 2,300ms로 측정됐습니다. 원인을 분석한 결과, 장바구니 아이템 N개 조회 시 Product와 ProductOption이 각각 N번씩 추가 조회되어 아이템 10개 기준 총 21개의 쿼리가 발생하는 N+1 문제였습니다.

Lazy Loading으로 설정된 연관 엔티티를 서비스 로직에서 반복 접근하는 구조였기 때문에, 아이템 수가 늘어날수록 쿼리 수가 선형으로 증가하고 동시 사용자가 많아질수록 DB 부하가 급격히 커지는 문제였습니다.

[해결 방안] Querydsl로 Product와 ProductOption을 fetch join해 단일 쿼리로 통합 조회하는 findBasketsByAccountId를 Repository 계층에 구현했습니다. 해당 API는 페이지네이션 없이 계정 단위로 전체 조회하는 구조여서 fetch join의 중복 row 이슈가 없었고, DTO Projection으로 필요한 컬럼만 선택해 메모리 사용도 함께 최적화했습니다. 개선 후 동일한 k6 시나리오(50 VU)로 재측정해 수치를 검증했습니다.

[결과] 아이템 10개 기준 쿼리 21개 → 1개, p95 응답시간 2,300ms → 120ms (약 95% 개선), 50 VU 동시 부하에서도 p95 < 200ms 안정적 유지

Stateless JWT의 구조적 한계 극복 — Redis Blacklist 패턴으로 로그아웃 즉시 토큰 무효화

[문제 상황] JWT는 Stateless 구조상 한번 발급된 토큰은 만료 전까지 서버에서 취소할 수 없습니다. 로그아웃 후에도 탈취된 Access Token으로 재인증 없이 API를 호출할 수 있는 보안 공백이 존재했습니다. 그렇다고 DB에 토큰 상태를 저장하면 모든 요청마다 DB를 조회해야 해 JWT를 쓰는 이점이 사라지는 트레이드오프가 있었습니다.

보안을 강화하려면 서버 상태를 유지해야 하고, 상태를 유지하면 성능이 희생되는 구조적 모순이 있었습니다.

[해결 방안] Redis를 활용해 두 가지 전략을 조합했습니다. Refresh Token은 Redis에 TTL과 함께 저장해 만료 관리를 DB 없이 처리하고, 로그아웃 시에는 해당 Access Token을 Redis Blacklist에 잔여 만료 시간만큼의 TTL로 등록했습니다. 이후 요청마다 Blacklist 존재 여부를 확인해 폐기된 토큰의 재사용을 차단합니다. 토큰 서명에는 HS256 대신 HS512를, 비밀번호 해싱에는 BCrypt strength 12(기본값 10)를 적용해 무차별 대입 공격에 대한 내성도 강화했습니다.

[결과] Stateless JWT의 구조적 한계를 Redis로 보완해 로그아웃 즉시 토큰 무효화 달성, DB 조회 없이 인메모리 캐시로 Blacklist를 확인해 성능 영향 최소화

외부 데이터 장애에도 끊기지 않는 시세 파이프라인 — WebSocket·REST Fallback·TTL 정책

[문제 상황] 국내외 시장은 거래 시간과 데이터 제공 방식이 다르고, 시세·지표·뉴스마다 요구되는 최신성과 외부 API 호출 제한도 달랐습니다. 모든 데이터를 동일한 주기로 조회하면 장 마감 후에도 불필요한 호출이 반복되고, 외부 API 장애 시 화면 전체가 오래된 데이터인지 실패한 데이터인지 구분하지 못하는 문제가 있었습니다.

[해결 방안] 관심 종목의 국내 시세는 KIS WebSocket으로 수신하고 연결 실패 시 REST 스냅샷으로 전환했습니다. 가격·시장 지표·수급·재무·차트·뉴스마다 거래 시간과 데이터 특성에 맞는 갱신 주기와 TTL을 정의하고, 뉴스에는 Stale-While-Revalidate를 적용했습니다. 응답에는 수집 시각·원천·최신성·Fallback 여부를 메타데이터로 함께 전달했습니다.

[결과] 장 마감 후 불필요한 호출을 줄이고, 외부 데이터 소스 장애 시에도 마지막 정상 데이터를 유지했습니다. 화면에서는 실시간·지연·대체 데이터 상태를 구분해 보여줄 수 있도록 구성했습니다.

불완전한 분석 결과의 게시 차단 — 4개 분석 엔진과 Semantic Quality Gate

[문제 상황] 기술·수급·재무·심리 데이터를 종합한 분석 신호는 일부 원천 데이터가 누락되거나 fallback 값으로 대체돼도 직렬화 자체는 정상적으로 완료될 수 있었습니다. 이 상태로 결과를 캐시하면 불완전한 분석이 정상 신호처럼 사용자에게 노출되는 문제가 있었습니다.

[해결 방안] 기술, 수급, 재무, 심리 엔진을 분리하고 각 엔진에 필수 지표·데이터 상태·원천 정보 규칙을 정의했습니다. 주식과 ETF의 평가 정책을 구분하고 엔진 간 수급 등급과 재무 상태의 일치 여부까지 검사하는 Semantic Quality Gate를 구현했습니다. 품질 검사를 통과한 결과만 Redis에 저장하며, 분산 락·작업별 timeout·health 상태로 갱신 작업의 중복 실행과 부분 실패도 통제했습니다.
